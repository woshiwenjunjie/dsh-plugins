# 便签颜色语义化：工程路径与兼容性代价

> 评估对象：`@woshiwenjunjie/dsh-sticky-notes` 0.1.16，源码 `plugins/dsh-sticky-notes/lib/client.js`。
> 结论先行：**推荐「纯视图层映射 + 代码内冻结的颜色→语义表」（A）**；不推荐「弱约定」（C）当工程方案；
> 「新增字段」（B）只有确认「同一颜色必须承载多种语义」时才值得付，且必须先做 `patchNote` 收口。

## 1. 现状事实（源码核实）

数据模型：
- 颜色是单个字符串 id，5 值：`COLOR_IDS = ['amber','sky','mint','rose','violet']`（:79）。
- `normalizeNote` 只校验色名，未知值回退 `amber`（:93）；它是 `readNotes` 与 `parseBackup` 的唯一入口（:115、:264）。
- 新便签是**随机取色**（addNote :1848）——颜色今天没有语义。
- 落盘只写 `{ notes }`（writeNotes :135-143）；备份顶层 `{format, version:1, exportedAt, notes}`（:247-249）。

写回路径是「手写字段白名单」，共 8 处，这是本任务最贵的事实：
addNote :1845 · updateNote :1897 · commitNote :1918 · cycleColor :1928-1930 · togglePin :1941 ·
archiveNote :1954 · unarchiveNote :1966 · renumber :1090-1100。
→ **新字段只在 normalizeNote 里加一次不够**；漏任一处，用户一次拖动/置顶/换色/编辑就把它洗掉。
`renumber` 尤其隐蔽：拖动排序与「按最近改动重排」都走它。

渲染与样式：
- 卡片类名 `dsn-note dsn-c-<color>`（:1174），颜色来自 CSS 变量 `--dsn-sticky`（:2682-2686，五个固定 hex，不随主题变）。
- 换色按钮 `.dsn-dot-btn`（:1319-1329），title/aria-label 是「换个颜色」。
- `NoteCard` 是 `memo` 的（:1378），父组件必须保持 props 引用稳定。
- 颜色只出现在左侧 3px 色条与底部小圆点，**纯装饰**，今天不承载信息。

备份/合并：
- `parseBackup` **不读 `version`**（:252-268）——老版本会照样导入新备份，并丢掉不认识的字段。
- `mergeNotes` 按 id 整条替换、`updatedAt` 新者胜（:271-301），不做字段级合并。
- 两标签页同步靠 `storage` 事件比较整份 notes JSON（:1647-1662）；`writeNotes` 是整份覆盖写，不是增量。

测试现状：
- 四层 smoke / behavior / contrast / perf，但 `scripts/check.mjs:90` 只跑前三层，**perf 是手动层**。
- 备份往返断言只比 6 个字段（behavior.mjs:710-714）——新字段既不被验证、也拦不住丢失。
- 全测试目录 grep `onCycleColor|dsn-dot` = **0 命中**：换色交互今天零覆盖。
- contrast.mjs 用例集只有主题 token 对（:130-139），5 个色条颜色**不在门禁内**。
- Markdown 导出只写时间与置顶/归档标记（:2110-2141），**不含颜色**——语义化后这条「给人看」的出口会丢语义。

## 2. 三条技术路径

### A. 纯视图层映射（不改数据）— 推荐

- 改动点：新增模块级冻结常量 `COLOR_ROLE`（amber→「待办」、sky→「进行中」…），只在渲染层使用：
  卡片语义标签、色条 title、筛选 chip、分组头、统计。数据里仍只有 `color`；`addNote` 的随机色改成固定默认（否则新便签语义随机）。
- 数据模型：不变（仍是 5 值字符串）。语义表在代码里，版本 = 插件版本。
- 兼容性：**零迁移**。老备份、老便签、老版本标签页、跨版本往返全部无感——旧版本只是不显示标签，颜色照旧。
  代价：语义表一旦发布就要**冻结 / 只追加**，改映射等于重新解释历史便签。

### B. 新增字段 `role`（或 `palette`）

- 改动点：`normalizeNote` + 8 处白名单（建议先抽 `patchNote(note, patch)` 用 `Object.assign` 收口，一次防住以后所有新字段）
  + 备份/合并/导入导出 + i18n + 换色按钮语义（颜色与 role 解耦后，「换色」与「改语义」是两个动作）+ 筛选/统计 + 迁移。
- 数据模型：note 多 `role: string|null`（枚举校验，未知回退 `null`，**不要**从 color 猜）。`color` 退回纯装饰；
  若两者保持 1:1，就退化成 A 的语义但多背一个字段。
- 兼容性：**被迫迁移**（至少是隐性迁移），见 §3 表格后四行。

### C. 弱约定（不改数据、不写映射表）

- 改动点：只改文案（tooltip/README 写「建议用这 5 种颜色分别代表…」）。
- 数据模型：无。
- 兼容性：零。但它**不能支撑筛选/分组/统计**：没有可复用的映射表，代码无从判断「这个颜色是什么意思」；
  约定会随用户与版本漂移，且完全不可测。只能作为 A 的文案补充，不能当方案。

## 3. 兼容性场景逐个推演

| 场景 | A 纯视图映射 | B 新增字段 | C 弱约定 |
| --- | --- | --- | --- |
| 老备份导入（只有 color） | 正常，无字段可丢 | `normalizeNote` 给 `role=null`，正常 | 正常 |
| 老便签无新字段 | 无字段，正常 | 视作无语义；**不要按 color 推断**，否则以后改映射会重写历史 | 正常 |
| 两标签页并存（同版本） | 无风险 | 安全：两边都写 role，storage 整份同步；现有「后写覆盖整份」窗口与字段无关 | 无风险 |
| 老+新版本标签页并存（升级后旧页没刷新） | 安全 | **危险**：旧版本 `normalizeNote` 丢掉 role，任何编辑触发 300ms 去抖整份写回，**全部 notes 的 role 一起消失** | 安全 |
| 导入合并冲突 | 无字段 | 整条替换（:290-293）：若老备份里同 id 更「新」，会用无 role 的老条目整体覆盖带 role 的条目 → 语义丢失 | 无字段 |
| 导出→老版本导入→再导出 | 无损（只有 color） | 语义在往返中蒸发，旧版本不报错不提示，用户无感 | 无损 |
| 换色/置顶/拖动/编辑 | 无影响 | 漏改白名单就洗掉字段（renumber :1085-1103 必踩） | 无影响 |

哪些方案会被迫迁移、迁移怎么写才安全：
- 只有 B 需要迁移。安全写法：**读时惰性默认**（normalizeNote 一处），不要写时回填；迁移只在内存发生，老数据原样保留。
- 若必须回填：先自动导出备份 → 一次性、幂等 → 复用 5 秒撤销通道给用户后悔 → 加 `schema:2` 只能给新版本自己识别，
  **旧版本不会拒绝**（parseBackup 不校验 version）。
- 迁移必须能「从 color 重建语义」，否则旧版本一出场就永久丢失；这反过来说明：**如果语义必须能从 color 重建，
  B 相对 A 的唯一增量就只剩「同色多义」**。README/CHANGELOG 要写明「跨旧版本往返会丢语义字段」，别指望代码阻止。

三条红线：
1. 不得把语义只存在 note 上而不留「可从 color 重建」的兜底——旧版本会清空。
2. 不得在旧版本仍在用的窗口里发布「只把语义写在数据里」的版本（升级未刷新是常态）。
3. 颜色若承载信息就不能只靠颜色（WCAG 1.4.1 / 1.4.11）：实测 5 色对卡片底（浅色 `#f5f5f5`）只有
   amber 1.74、mint 2.17、sky 2.53、rose 2.52、violet 2.51，**全部低于图形元素 3:1**；深色 `#2a2a2a` 为 5.19–7.56 达标。
   所以必须配文字/分组头等非颜色冗余，否则浅色主题下语义不可读。

## 4. 性能

实测 `node test/perf.mjs 300 60`（假 React，Node 内相对值；本机基线波动 0.24–0.30ms）：

| 改动 | elementsSteady | cardsSteady | msSteady |
| --- | --- | --- | --- |
| 基线（300 条） | 54 | 0 | 0.24–0.30 |
| 每张卡多 1 个稳定 prop | 54 | 0 | 0.63–0.67 |
| 每张卡多 2 个 prop | 54 | 0 | ≈0.55（同量级） |
| 视图层语义标签（不发 prop，card 内用 note.color 解算） | 54 | 0 | 0.28–0.29 |
| 额外一条 colorCounts `useMemo([notes])` | 54 | 0 | ≈0.38（同场基线持平） |

（500 条基线 msSteady ≈ 0.41。）

原则：
1. **不要给 memo 卡片新增 prop。** 现有代码踩过：来源会话标签只在需要时才挂 prop（:2526-2532 注释，实测 0.4→0.8ms）。
   A 的标签可在 `NoteCard` 内用**已有的** `note.color` 解算，props 形状完全不变 → `cardsSteady` 仍为 0、稳态不掉。
2. 新增 prop 的代价不在渲染，而在「每次父渲染 × 每张卡 × 浅比较多一个 key」：300 条约 +0.3ms，500 条线性放大；
   1 个和 2 个差别不大，**只要多一个就接近翻倍**，所以「只在需要的卡片上挂」是唯一可接受的形态。
3. 按颜色筛选/分组/统计本身是 O(n)，必须 memo 在 `[notes, colorFilter]` 上，筛选与计数一次遍历完成；
   300 条是微秒级，不进稳态。分组头最多 5 个 host 元素/次渲染，相对 `elementsSteady=54` 可忽略。
4. 两个交互坑：
   - `filteredNotes` 在搜索态**绕过 baseList**（:1522-1533）：颜色筛选只加到 baseList 会被搜索静默忽略，要加就两条路径都加。
   - 语义模式若做成全局开关又通过 prop 下发，就等于给每张卡加 prop；要么 opt-in 时才挂 prop，要么别进 cardProps。

## 5. 可测试性

| 方案 | 需要的测试层 | 内容 |
| --- | --- | --- |
| A | smoke + behavior + contrast + perf | smoke：5 色与无语义老数据都渲染、class 名不变；behavior：新建默认色、换色循环、颜色筛选×搜索组合、分组顺序、旧版本 payload 容错；contrast：**新增** 5 色 vs 卡片底 ≥3:1 + 语义标签文字 ≥4.5（今天会失败，正好暴露红线）；perf：`cardsSteady=0`、`msSteady` 不回归 |
| B | 同 A，外加 8 条「字段存活」断言 | 打字/失焦/置顶/归档/恢复/换色/拖动/按时间重排各一次后 `role` 仍在；导入导出往返带 role；老备份合并后 role 不被洗；模拟「storage 里写入无 role 的 notes → 新版本如何容错」 |
| C | 只能测文案 | 筛选/统计无从测起，等价于不可测 |

最容易漏的回归（按概率）：
1. 换色/拖动后新字段消失（renumber 与 cycleColor 白名单）——B 的头号漏洞。
2. 「老版本标签页」场景没人测：需要一条「写入无 role 的 notes → 新版本容错」用例。
3. `cardsSteady` 回归不进 CI（check.mjs 不跑 perf），只能靠人记得。
4. 颜色筛选在搜索态失效（filteredNotes 两条路径）。
5. 对比度门禁不含 5 个色条颜色，语义化后没人拦。
6. 新建随机取色（addNote :1848）与「默认语义」冲突，behavior 里没有任何断言盯着它。

## 6. 结论表

| 方案 | 成本 | 风险 | 是否需要迁移 | 结论 |
| --- | --- | --- | --- | --- |
| A 纯视图层映射 | 小：1 个常量 + 渲染层 + 文案 | 极低：数据不变；风险是改映射会重解释历史 | 不需要 | **推荐** |
| B 新增 role 字段 | 大：8 处白名单 + normalize + 备份 + i18n + 筛选 | 高：旧版本标签页、拖动重排、老备份合并三条丢失路径 | 需要（隐性迁移） | 条件触发；先抽 `patchNote` |
| C 弱约定 | 极小：只有文案 | 零数据风险，但语义漂移、不可测、撑不起筛选/统计 | 不需要 | **不推荐当方案**，只做 A 的补充 |

A 的最小闭环：① 模块级 `COLOR_ROLE` 常量 + 「冻结/只追加」注释；② 卡片语义标签（用 `note.color` 解算，不加 prop）；
③ 筛选 chip 与计数（memo 到 `[notes, colorFilter]`，搜索两条路径都生效）；④ `addNote` 改固定默认色；
⑤ 对比度：语义标签文字过 4.5，色条只当辅助；⑥ 测试补齐换色/筛选/对比度，并把 perf 的 `cardsSteady=0` 变成门槛。
