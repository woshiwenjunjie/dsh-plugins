# 语音输入 & 剪贴板快速记录：反方评审（product critic）

> 角色：反方。审的是「要不要做」，不是「怎么做」。方法：先把现有交互的动作数与像素量出来，再把两个功能放进三个真实瞬间里称，最后用一套可复用的门槛打分。
> 文中行号均指 `plugins/dsh-sticky-notes/lib/client.js`（本机 2848 行版本）。

## 0. 结论先行

- **语音输入：不做。12/25，两条硬门槛同时失守。** 首次 239MB 下载 + 录音状态机 + 中文口述改稿，三项成本全压在「说 15 个字」这个动作上；而它换来的能力（把说的话变成文字）在同一个焦点框里已经有两处供给（DSH 官方聊天框语音、系统级听写）。
- **剪贴板快速记录：缩小范围做，只做「填进草稿」，不做「直接建卡」。20/25，唯一过线的形态。** 它唯一真省事的瞬间是「屏幕上已有一段长文本、我不想离开当前输入框」，那个瞬间能从 4 个动作降到 1 次点击。
- **比「不做」更硬的禁止项：** 全局监听 `paste` 事件；以及任何「点一下就把剪贴板内容直接落成便签」的设计。前者会把用户往聊天框里粘的 API key 顺手抄进便签，后者让剪贴板成为明文密钥的落盘通道（localStorage → JSON 备份 → Markdown 导出）。
- **现有数据基础不支持语音这个决定**：`METRIC_KEYS`（377 行）里没有长度、没有放弃率、没有粘贴，任何「用户需要口述」的判断都只是猜。
- 读法：瞬间 §1、失败清单 §2、标准与打分 §3–4、唯一值得做的最小版本 §5、明确不该做 §6、非做不可的坑 §7、面板成本账 §8、重开条件 §9。

## 1. 三个真实瞬间

先确认一条被忽略的基线：**面板一打开，草稿框就已经聚焦了**（1924–1938 的 effect，注释写的是「唤起即写」）。所以「打字」这条主路径是 **0 次点击**，任何新入口都是在 0 上加成本。下面每个瞬间都按这个基线数动作。

### 瞬间 1：读文档时冒出一句话要记（手在鼠标上，面板关着）

- 现在：`Alt+Shift+N` →（焦点已在草稿）→ 打字 → `Ctrl+Enter` = **2 个组合键 + 打字**。
- 剪贴板：只有「他刚复制过东西」才有意义。`Alt+Shift+N` → 点粘贴按钮 → `Ctrl+Enter` = 1 组合键 + 1 次点击 + 1 组合键。**比原生 `Ctrl+V` 少按一个键，却多一次鼠标定位，净收益 ≈ 0。**
- 语音：点麦克风 → 说 → 点停止 → 等 1–3s → 改错 → `Ctrl+Enter` = **2 次点击 + 等待 + 校对**。为 15 个字付这些，是纯亏。
- 判定：这一格，**两个功能都是多此一举。**

### 瞬间 2：聊天框里粘来一段 2000 字报错/日志/URL，想留一条

- 现在：选中 → `Ctrl+C` → `Alt+Shift+N`（焦点跳走）→ `Ctrl+V` → `Ctrl+Enter` = **4 个动作、2 次焦点迁移**。
- 剪贴板：**1 次点击，焦点不离开聊天框**。省 3 个动作，而且这段文本本来就寄居在剪贴板这个「临时家」里。
- 语音：完全不适用（文本已在屏幕上，念一遍比复制慢一个数量级）。
- 判定：**剪贴板的全部价值就在这一格。** 它省的是「焦点迁移」而不是「按键」——所以形态必须是「点一下就好」，绝不能是「开面板、点输入框、再点按钮」。

### 瞬间 3：手上有东西或离键盘远，只想说一句

- 现在：走回键盘。
- 语音：点麦克风说 5 秒——**这是唯一真省事的格子，我不否认它存在。**
- 判定：成立，但这是本插件**最窄的一格**。DSH Web 是桌面 Chat 应用，键盘鼠标就在手边；而这一格最不该出现的东西恰恰是「首次 239MB 下载」——用户最急着说一句话的时候，产品让他先等下模型。

## 2. 失败模式清单

### A. 语音输入

1. **首次 239MB 的期望管理崩了。** 一次误触（尤其「长按说话」）就触发下载；面板里没有进度位（`dsn-head`/`dsn-composer` 里没有任何常驻状态区），而唯一的提示通道 toast 最长只活 4000ms（`showToast` 的调用点 4000/3200/2400，`UNDO_MS` = 5000）——**一个可能几分钟的下载，全靠一个 5 秒后会消失的条**。用户看到的是「点了没反应」，然后关了面板。int8 239MB / fp32 937MB 的落差还会让一部分人反复点重试。
2. **识别错误率 × 改稿成本 > 打字成本。** 便签的典型长度是十几个字。短句里错一个专有名词（文件名、API 名、人名），改法只能是整句重读重打——**改稿成本超过了原本的打字成本**。300px 宽、`max-height: 420px`（938 行）的草稿框里做光标定位与局部替换，比在 IDE 里难受得多。
3. **中文口语会原样进来。** 「嗯 / 那个 / 就是 / 然后」ASR 照转，转完要人删；口述天然是流水句，而便签的可用形态是短句 + 换行 + `#tag`。更具体的坑：`TAG_PATTERN` 只认 `#` 后紧跟字母数字（1028 行），口述「#工作」很可能变成「井号工作」或全角「＃ 工作」——**标签静默失效，不报错，只是以后搜不到**。
4. **无麦克风 / 权限拒绝。** Electron 里 `getUserMedia` 要过系统麦克风权限（Windows 隐私设置）。拒绝后若不给明确文案，用户只会认为按钮坏了——而本项目对「失败必须如实说」是有先例的：`toast.copyFailed`（2213）、`saveFailed` 红字（1755、173–176）。
5. **环境噪音。** 录音时恰好是他在 DSH 里打字最密的时候，键盘声会被当成顿或噪声；办公室人声可能直接进正文。这类错误不会「失败」，只会产出**看起来对但内容错了**的便签——比崩溃更坏。
6. **长按 vs 点击的状态机。** 同一个按钮上两种手势会互相误判（点慢了变长按），需要阈值 + 明确视觉；而这套状态机还要被 Esc、点面板外面（1886–1907 的 pointerdown 监听会直接收起面板）、关面板、切标签页正确打断。
7. **快捷键冲突。** `Ctrl+Enter`（2498）、`Ctrl+K`（1865）、`Alt+Shift+N`（1912）已被占用；`Ctrl+V` 是草稿框原生粘贴、`Ctrl+Shift+V` 是浏览器的纯文本粘贴，两个都不能碰；中文输入法还常占用 `Alt+Shift+字母`。任何绑定都必须在 `isComposing` 时放行（2497 有先例）。
8. **cloud provider 直接把隐私承诺变成假话。** README 第 9 行与第 176 行写的是「数据只存本机浏览器 localStorage：**不经 Host、不上报、不发网络请求**」。接 host 侧 `speechToText` 经 `/_dsh/dsh-sticky-notes/*` 调，**本身就违背「不经 Host」**；若宿主配的是云端 provider，音频直接出本机。而便签里说的话往往正是不会打进聊天框的那种内容——**风险最高的内容走了风险最高的通道**。
9. **录音被误触。** 一张 300px 卡片脚部已经挤了置顶、色点、归档、复制四个按钮（1365–1428），点击密度很高；误点开麦后如果没有强提示，就是「在录音但用户不知道」。
10. **录音中卸载不释放麦克风。** 关面板走的是 `open` 变 `false`（2383 行整棵面板不构造），React 卸载不会自动 `track.stop()`；系统麦克风指示灯会一直亮，而用户第一反应是「它在偷录」。
11. **识别结果直接建卡 = 污染数据。** 半句话、识别错的句子会变成一条真便签，进列表、进回顾条（`pickReviewNote` 会挑中它，242–254），而纠错窗口只有 5 秒 undo（`UNDO_MS`）。
12. **埋点也没地方放。** 想加 `voice` 指标要先改 `METRIC_KEYS` 白名单（377），否则 `recordMetric` 直接丢弃（411）；而 Markdown 导出的尾部带本机统计（README 72）——「用过几次语音」会跟着导出文件走。

### B. 剪贴板捕获

1. **权限与手势。** `readText()` 需要用户手势 + Chromium 的 `clipboard-read` 权限。DSH 自家 Excel 预览用过说明**技术上可用**，但被拒时不能静默：`writeText` 那侧的失败提示已经写了（2213、2218–2225），读侧要有对称的三分文案。
2. **空剪贴板 / 只有图片。** `addNote` 对空串是**静默 return**（1976–1977），而「记下」按钮本身在草稿为空时是 disabled（2517）。所以「点粘贴 → 什么都没发生」会和「按钮坏了」完全同形。有图时 `readText` 同样拿不到文本。
3. **富文本。** `readText` 只给纯文本 → 列表、代码块、表格格式全丢。这其实不算失败（`.dsn-note-view` 是 `white-space: pre-wrap`，2942，缩进还在），但要清楚「粘进便签」永远不等于「格式保留」。
4. **超长。** 一整页文档、一条几十万字符的日志 → 卡片高度封顶 420px（938）、localStorage 5MB 配额（`writeNotes` 的 catch，173–176）、JSON 备份与 Markdown 导出体积同比放大。`MAX_NOTES = 500`（72、1994）**只限条数不限字节**，它挡不住单条 2MB 的粘贴。
5. **重复内容。** 同一次复制点两次 = 两条一模一样的便签。去重需要 hash，而 hash 是 note 字段——**不能加**（§3 M3）；只能退化成在内存里比 `lastText`。
6. **误把敏感内容记进来（唯一会造成真实损害的一条）。** 复制密码 / 私钥 / token 之后顺手点一下，明文就进了 localStorage，再进 JSON 备份、Markdown 导出、甚至 docs 目录里的示例文件。README 把备份称作「唯一的安全网」（136），这里它会变成**唯一的泄漏路径**。
7. **全局 `paste` 监听（最危险的设计）。** 为了「不点按钮」而监听 window 的 paste，用户往聊天框粘 API key 时也会被记成便签。这条必须写死在「明确不做」里，不是「不优先」。
8. **多标签页并发。** `storage` 事件（1766–1782）能同步，但写入是 300ms 去抖后**整份覆盖**（171），两边同时写就是最后写者赢、无冲突提示。更隐蔽的是 origin 分裂：剪贴板是**全局**的，便签是**本 origin** 的（README 186 已写明 `127.0.0.1` 与 `localhost` 不互通）——在 localhost 复制、在 127.0.0.1 粘贴，用户会以为丢了一条。
9. **与原生 `Ctrl+V` 的焦点冲突。** 面板打开时草稿框已聚焦（1935），任何全局粘贴快捷键都会先撞上 textarea 的原生粘贴，结果是「粘进草稿」而不是「新建一条」。这不是 bug——**它恰恰证明主路径已被原生粘贴覆盖**。
10. **来源身份不明。** 便签的「来源会话」靠 `sessionId`（1988）。粘贴进来的文字会被标成「本会话」，而它真实来源是某个网页或某次复制——一个看起来精确、实际错误的元信息。

## 3. 决策标准（M1–M5）

沿用颜色评审的 K 系口径（零教育、不破坏随手记），换成这两个功能真正会踩的门槛。每条 1–5 分；**M3 或 M4 ≤ 2，或 M5 ≤ 2，直接否决**。

- **M1 零教育**：不需要任何说明文字就能第一次用对；第一次使用正确率可以靠「点一下就知道」达到。
- **M2 不破坏随手记**：不夺焦点、不阻塞「打开即写」、不在首屏抢列表空间；录音/粘贴态可被 Esc 与点外面取消。
- **M3 零新增 note 字段、备份格式不变**（硬门槛）：白名单在 7 处手写（1980、2032、2053、2065、2093、2106、2118），漏一处就被拖动/置顶/换色洗掉；且未刷新的旧标签页会用整份覆盖写吞掉新字段。
- **M4 本机承诺不变**（硬门槛）：不经 Host、不上报、不发网络请求（README 9/176）。
- **M5 净收益**：省下的动作数 > 新增的动作数；按 §1 的瞬间逐个称，不能只挑最好的那一格。

## 4. 打分

| 方案 | M1 | M2 | M3 | M4 | M5 | 合计 | 判定 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| V1 语音输入（复用 host `speechToText`） | 2 | 2 | 5 | 2 | 1 | 12/25 | ❌ M4/M5 双门槛失守 |
| V2 语音 + 只允许本机 provider + 结果只进草稿 | 2 | 2 | 5 | 4 | 1 | 14/25 | ❌ 仍卡在 M5 |
| C1 剪贴板 → 直接建一条便签 | 3 | 3 | 5 | 5 | 3 | 19/25 | ⚠️ 过线但敏感内容直接落盘 |
| C2 剪贴板 → 填进草稿（不建卡） | 4 | 3 | 5 | 5 | 3 | 20/25 | ✅ 唯一及格 |

读法：C2 比 C1 只多 1 分，但那 1 分是「内容在落盘前被用户看过一眼」——**密码不会被顺手存下来**，这条比分数重要。V2 已经是我能给语音的最优形态（去掉 cloud、结果进草稿），它仍然输在 M1 和 M5：首屏永远要为一个「每 200 次记录用 1 次」的入口付位置费。

## 5. 唯一值得做的最小版本

**草稿框脚部加一个 24×24 的「粘贴剪贴板」图标按钮：点一下把剪贴板里的文本插入草稿（不建卡、不夺焦点、复用既有 32px 行高），空/非文本/超长三种情况各用现有 toast 通道如实说一句。**

可验收（5 条，全部可在现任测试脚本里跑）：

1. 空剪贴板点击 → 出现「剪贴板里没有文字」，且列表条数不变（现在 `addNote` 对空串静默 return，1976）。
2. 复制 3000 字后点击 → 草稿只插入前 2000 字 + 一行「已截断」，**不新增便签**（保护 5MB 配额与 420px 卡高，173–176 / 938）。
3. 面板打开时首屏可见条数与改动前一致：新增像素高度 = 0（按钮复用 `dsn-composer-foot` 的 32px 行，2504–2521）。
4. 无新增 note 字段、无新增 localStorage key、备份 JSON 与 Markdown 导出格式不变；`node test/behavior.mjs` 与 `node test/perf.mjs` 仍通过。
5. 复制一段密码再点 → 内容进草稿但**不自动落盘**，要按 `Ctrl+Enter` 才成为便签——这就是「填草稿」相对「直接建卡」的全部价值。

## 6. 明确不该做的一件

**语音输入（包括「只接本机 ONNX、不接 cloud」那版）。**

一句话理由：239MB 首次下载 + 录音状态机 + 中文口述改稿，三项成本全押在「说 15 个字」上；而它要买的那个能力在同一个焦点框里已有供给——DSH 官方语音把文本插进聊天输入框，系统级听写（Win+H / 双击 Fn）作用于任何聚焦输入框，**包括本插件的草稿框**。插件唯一能加的增量是「变成一条便签」，而这一步用剪贴板路径更便宜、且不违背「不经 Host」。

附一条必须承认的反证：系统听写在 Electron 里对草稿框是否可用**我尚未实测**。如果要做语音，这一条应当先被验证——它若成立，语音的增量就只剩「没装系统语言包的用户」，那更不值得 239MB。

## 7. 若非做不可：必须先写进设计的坑

1. 239MB 只能由用户在语音设置里显式确认；面板内点击最多跳设置，绝不就地触发下载。
2. 下载进度不能复用 toast（上限 4000ms），必须新增一条常驻状态行并带「取消」。
3. 录音只有一种手势：点击开始 / 点击结束；Esc、点面板外面、关面板、切标签页 全部等于取消并释放麦克风。
4. 60 秒硬超时 + 可见计时，杜绝「麦克风一直亮着」。
5. 识别结果只进草稿（复用 `DRAFT_KEY` 与 `Ctrl+Enter`），绝不直接 `addNote`；落盘前用户能看见、能改、能整段丢。
6. 无麦克风 / 权限拒绝 / 模型缺失 / 转写失败 四种文案分开，全走 `toast.error`（比照 2213）。
7. 只允许本机 provider；宿主只配了云端时按钮直接 disabled + 一句说明，禁止静默上传。
8. 快捷键只用 `Alt+Shift+V`，`isComposing` 时放行（2497 先例）；禁止占用 `Ctrl+V` / `Ctrl+Shift+V` / `Ctrl+K` / `Ctrl+Enter` / `Alt+Shift+N`。
9. 禁止全局 `paste` 监听；剪贴板只能由一次显式点击读取。
10. 粘贴超过 2000 字符截断；写失败沿用 `saveFailed` 红字（1755），不新增错误通道。
11. README 第 9/176 行那句「不经 Host、不发网络请求」必须同步重写，否则承诺就是假的。
12. 上线前先给 `METRIC_KEYS`（377）加 `voice`，否则这功能连「该不该留」的数据都没有。

## 8. 300px 面板与「简洁」的成本账

量出来的现状（面板宽 `min(300px, …)`，2838；内容可用宽约 272px）：

| 区块 | 高度 | 依据 |
| --- | --- | --- |
| 头部（标题 + 3 个 32px 按钮） | ≈ 56px | 2840，padding 14/10 |
| 草稿区（rows=3 + 脚部 32px） | ≈ 130px | 2488、938、2894 |
| 筛选行（全部/本会话/归档） | ≈ 34px | 2889–2890 |
| 搜索行（≥6 条才出现） | ≈ 40px | 74、2863 |
| 回顾条 | ≈ 38px | 2905，min-height 30 |
| **固定吃掉** | **≈ 298px** | 900px 视口下列表 ≈ 600px ≈ **7 张卡片**；750px 笔记本只剩 ≈ 450px ≈ **5 张** |

三种新增形态的代价：

- **(a) 塞进现有 `dsn-composer-foot` 行**：**+0px**，首屏条数不变。代价是 272px 里要放 提示 + 新按钮 + 「记下」（约 76px）；中文短提示够用，但英文长错误文案（"Couldn't copy — select the text manually"）会把 hint 挤成两行，`dsn-hint` 必须允许换行或省略号。
- **(b) 独立录音条（波形 + 计时 + 停止 + 取消）**：**+44~56px ≈ 0.6 张卡片**，首屏 7 → 6。
- **(c) 首次下载提示行**：再 **+40~60px**（300px 宽一句中文约 20 字/行，隐私+下载说明起码两行），首屏 7 → **5**。这一档就是「把列表挤下去」。

还有两处空间已经用掉了：收起态只有 32px 宽，`dsn-tab-draft` 是绝对定位的角点，注释写着「便签栏只有 32px 宽，多一行会显得臃肿」（2372）；头部按钮数量是靠把备份/重排收进 `⋯` 才保持不变的（2420）。**任何常驻语音入口都与这两条既有取舍直接冲突。**

更要紧的是这个仓库自己的规矩：搜索要等到 6 条才出现（73–74）、颜色筛选塞进搜索行而不是另起一排（2584 注释「首屏仍然留给列表」）、低频操作收进 `⋯`（2420）。**把「每 200 次用 1 次」的语音按钮摆在全插件最贵的首屏，是这套规矩的第一个例外**——一旦开了，下一个功能也会要求同样的位置。

## 9. 什么条件下该重开这个话题

- 只有出现下面两条之一，语音才重新值得讨论：**（a）`metrics` 显示 80 字以上长便签占比 > 15%**；**（b）有用户明确说「我在便签里记长段内容」**。两条现在都没有证据，因为 `METRIC_KEYS`（377）根本没记长度。
- 剪贴板则随时可以做，且**不需要新数据**——它服务的是「已经复制过的文本」，这个行为在现有 `create` 计数里已经隐含。
- 顺序建议：C2 剪贴板填草稿（1 个按钮、0 像素）> 什么都不做 > 任何语音方案。
